## 认证/授权/SSO 架构分析与演进规划（19:53）
- 用户提出四大议题：认证放 gateway 还是 authorization、授权在网关做过滤器、consul/nacos 无法 native 故自研 discovery、限流同理轻量自研。要求做整体规划。
- **产出**：`docs/网关认证授权演进规划.md`（现状盘点 / 认证归属论证 / P0–P6 路线图 / native 硬约束 / 待决策）。
- **核心结论**：认证（签发）只在 `autumn-gateway-authorization`；网关只做 JWKS 验签 + 身份透传 + 路由级粗粒度鉴权；细粒度与数据权限留在业务服务。网关不自己写登录（否则 SSO 失效、网关变重、与 native 轻量目标冲突）。
- **发现的 P0 隐患（此前未记录）**：系统里现有**两套互不认识的令牌**——
  dashboard 自签 HS256（`jwt.secret` 明文硬编码、sub=数字 userId、**claims 无 authorities**）vs authorization 签发 RS256（JWKS 落 `oauth2_jwk`、sub=uuid、带 authorities）。
  不收敛的话网关要维护两套 JwtDecoder、两种 sub 语义、且 dashboard token 无权限码导致网关必须回查库。
- 已向用户提出 3 个待决策：① dashboard 令牌是否并入 authorization（建议是）② 权限码放 token 还是网关查缓存（建议 token 带 authorities 版本号）③ 网关权限数据直连库还是走 dashboard 内部接口。
- 微信场景已澄清三类（小程序 jscode2session 不是 OAuth2 / 公众号 snsapi_userinfo / 开放平台 snsapi_login，当前实现的是第三类）。

## RBAC 权限数据补齐：修复「admin 也没办法管理授权」（20:26–20:40）
- **根因**：`PermissionService#allMenuIdentifications` 用 `basic_menu.menu_identification` 装配超管 authorities，而库里是单段 `user`/`role`/`menu`，代码 `PermCodes` 用三段 `system:user:create`，`@PreAuthorize` 字符串精确比对失败 → 超管也被拒；前端 v-auth 同理不渲染。
- **现场数据**：basic_menu 13（按钮 type=3 为 **0**）、basic_resource 2、basic_menu_resource **0**、basic_role_permission 3、basic_user.login_error_count=0、basic_user_role 有 user_id=1559/10 的脏行；V1 唯一键只补了 uk_menu_resource 和 user_role.uk_user_role_app。

- **产物**：`db/rbac/V4__rbac_fix_and_grant_mysql.sql`（纯 DML、NOT EXISTS 判重、应用账号可跑、幂等）+ `db/rbac/V4__rbac_unique_keys_mysql.sql`（唯一键，需 root，未执行）。
- **执行**：用隔离 venv 的 pymysql 在事务里跑，先 JSON 备份 11 张表到 `/tmp/rbac_backup_20261021-203204.json`，失败自动回滚。已提交。结果：菜单 13→54、按钮 0→41、资源 2→37、关联 0→48、授权 3→197；admin/admiin 各 51 菜单+37 资源。

- **复核结论（任务1）**：`autumn-gateway-authorization` **零 jjwt 依赖**，5 个 JWK 类全用 `com.nimbusds`，无需替换；jjwt 只残留在 dashboard 与 examples-security / examples-security-oidc。
