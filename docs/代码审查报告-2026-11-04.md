## 一、网关核心（authz starter / common）— 人工精读

### 高危

**G1｜JWT 无撤销机制：锁定/停用/降权用户的旧令牌在 TTL 内继续有效**
- `authz-autumn-gateway-starter/.../filter/AuthzGatewayFilterFactory.java:106-109` — `authenticate` 模式只验签不查库；`authorize` 模式每请求查角色，但**从不检查 `basic_user.status`**，且 `admin` claim 签发时固化。
- 账号被锁定（登录失败次数归零置 status=0）后，已签发的 24h 令牌仍全量放行；管理员被降级后 24h 内仍是 `claims.admin()=true` 直通。
- 修复：短 TTL access token + refresh token；或 token 版本号（`password_updated_at`/`token_version` 进 claim，验签时比对）；网关侧至少对 `authorize` 路由顺带校验用户 status。

**G2｜登录接口无 IP 级限流 + 验证码可关闭 + BCrypt 时序侧信道**
- `.../web/EndpointController.java:111-124` — 验证码 `enabled=false` 时登录只剩按账号锁定；攻击者换着用户名爆破不受任何限制。
- `.../web/AuthzLoginService.java:59-62` — 用户不存在时**不做 BCrypt 计算**直接返回，响应时间明显更短 → 尽管消息一致，仍可通过时序枚举有效用户名。
- 修复：接入已验证的官方 `RequestRateLimiter`（`autumn-gateway-examples-limit` 参照实现）对 `/gateway/endpoint/login` 按 IP 限流；用户不存在时也跑一次 dummy hash `matches()` 抹平时序。

**G3｜`fail-open` / `permitAll` 是路由级配置开关，误配即裸奔**
- `AuthzGatewayFilterFactory.java:143-149, 244-247` — 默认值正确（fail-closed），但 `Authz=..., fail-open=true` 或 `permitAll=true` 一旦被误配（如从别的路由复制），无任何告警。
- 修复：启动时/路由刷新时扫描并 WARN 日志列出所有 fail-open / permitAll 路由；生产 profile 下直接拒绝 permitAll。

### 中危

**G4｜`authorize` 模式每请求查库且无缓存，角色多时是串行 N+1**
- `AuthzGatewayFilterFactory.java:130-133` — `concatMap(role -> findResources(appCode, role.id))` 逐角色串行查询；每个 `authorize` 请求至少 1（roles）+ N（resources）次 JDBC 查询，每次都走 boundedElastic + 新连接。
- 修复：①角色→资源合并为一条 SQL（JOIN 或 `role_id IN (...)`）；②加 Caffeine 缓存（user+appCode → 权限集，TTL 60s，改权限时失效）——这正是既定待办「权限缓存/主动失效」；③`DataSource` 建议外部配连接池（当前裸 `getConnection()`）。

**G5｜登录失败计数有并发竞态，锁定可被并发请求绕过**
- `AuthzLoginService.java:76-84` — 「读 count → 计算 next → 写回」非原子，并发 N 个错误密码可能都读到同一剩余次数，实际只扣 1 次。
- 修复：改为单条 SQL 原子递减（`SET login_error_count = GREATEST(login_error_count-1,0)` 并在归零时锁号），或 `UPDATE ... WHERE login_error_count > 0`。

**G6｜验证码 Cookie 缺 Secure 属性（与 dashboard 同病）**
- `EndpointController.java:68-74` — `httpOnly + sameSite(Lax)` 已设，但没有 `.secure(true)`。
- 修复：按配置（生产 https 环境）开启 `secure`。

### 低危

**G7｜`AuthzCaptchaService` 内存存储仅适用单节点**（`:22` 注释已自知）：多节点扩容前需换 Redis；`purgeExpired` 只在 generate 时触发，攻击者高频刷验证码会不断触发 purge+clear，正常用户验证码被整体重置（DoS 面，低危，先加 IP 限流即可覆盖）。

**G8｜common 的 `CaffeineCacheUtil` 是示例级代码进了主干**
- `CaffeineCacheUtil.java:38-46` — `LOADING_CACHE` 回源返回 `"source_data_"+key` 假数据，谁误用 `getWithLoad()` 就把假数据当真；`get(key, Class)` 未检查类型直接强转；注释与行为不一致（`expireAfterAccess` 写成"写入后过期"）。
- 修复：删除 LOADING_CACHE 或让回源函数显式传入；`get(key, clazz)` 加 `clazz.cast()`；当前主干无调用方，风险主要是将来被误用。

**G9｜验证码答案比较用 `equalsIgnoreCase` 无恒定时间**——验证码价值低且一次性消费，可接受，不强求。

> 精读中确认做对的地方（不需要动）：只认 `Authorization: Bearer` 不收 query token；可信头先删后写防伪造；`AuthzJwtService` 强制 HS256 密钥 ≥32 字节、限定算法族无 `alg=none`/HS-RS 混淆；登录失败消息统一防账号枚举（除 G2 时序外）；JDBC 全部 PreparedStatement 参数绑定，SQL 可配置但只来自服务端配置；阻塞 JDBC 全部切 boundedElastic 不卡 event loop。
