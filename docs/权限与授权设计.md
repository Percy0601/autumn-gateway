# Autumn Gateway Dashboard — 授权（Authorization）设计

> 适用范围：`autumn-gateway-dashboard` 模块（管理控制台后端）。
> 版本基线：Spring Boot 4.1.1 / Spring Security 7 / Java 25 / Spring Data JDBC。
> 配套前端：`autumn-gateway-dashboard-ui`。
>
> 本文回答四件事：**谁能改什么**、**什么不需要管控**、**什么必须管控**、**新库怎么自举**。

---

## 0. 一句话结论

**认证**（你是谁）已完成：JWT + `JwtAuthenticationFilter`。
**授权**（你能干什么）本次落地，采用 **标准 Spring Security 方法级鉴权 `@PreAuthorize("hasAuthority('...')")`**，
权限码存 `basic_menu.menu_identification`，授权关系存 `basic_role_permission`，全部数据驱动、不发版可调。

管控分三档：

| 档位 | 覆盖 | 判定方式 |
|---|---|---|
| 🟢 **匿名放行** | 登录、验证码、退出、静态资源、健康检查 | `permitAll()` |
| 🟡 **认证即可** | 全部查询（GET）+ 新增/编辑（POST / PUT 主资源） | `authenticated()` |
| 🔴 **权限管控** | 授权类（assign-\*）、删除、启停、重置密码 | `@PreAuthorize` + 权限码 |

## 1. 需求对照

| 需求 | 落地方式 | 位置 |
|---|---|---|
| ① 明确「管理员可以修改的功能」 | 见 §2 清单；超管（`basic_user.admin=1` 或角色 `master=1`）**直通全部**，无需逐条授权 | `UserGrant#has` / `UrlAuthorizationManager` |
| ② 用户/角色/用户组/菜单/资源「新增」不重要 | 新增与编辑归入 🟡 认证即可，**不加 `@PreAuthorize`** | 各 Controller 的 `POST` / `PUT /{id}` |
| ③ 用户授权、角色授权、用户组授权、菜单授权要管控 | 归入 🔴，逐个挂 `@PreAuthorize`，共 **22 个端点** | 见 §3 |
| ④ 用户管理增加重置密码 | 新增 `PUT /api/system/basic/user/{id}/reset-password`，权限码 `system:user:reset-pwd` | `BasicUserService#resetPassword` |

## 2. 管理员可以修改什么（需求 ①）

「管理员」在本项目有两个层次，**都能改下面全部内容**，区别在于实现方式：

| 角色 | 判定 | 权限来源 |
|---|---|---|
| **超级管理员** | `basic_user.admin = 1`，或持有 `basic_role.master = 1` 的角色 | 代码短路放行，**不查授权表**。好处：新加菜单/接口不会因为「忘了给 admin 授权」而把管理员自己锁在门外 |
| **受控管理员** | 普通角色（如 `SYS_ADMIN` / `SECURITY_ADMIN`） | 完全由 `basic_role_permission` 的逐条授权决定 |

### 2.1 管理员可修改清单（= 🔴 权限管控清单）

| 模块 | 可修改项 | 权限码 | 端点 |
|---|---|---|---|
| 用户 | 分配角色 | `system:user:assign-role` | `PUT /user/{id}/roles` |
| 用户 | 分配用户组 | `system:user:assign-group` | `PUT /user/{id}/groups` |
| 用户 | 删除用户 | `system:user:delete` | `DELETE /user/{id}` |
| 用户 | 启用 / 停用 | `system:user:enable` / `system:user:disable` | `PUT /user/{id}/enable` `/disable` |
| 用户 | **重置密码**（本次新增） | `system:user:reset-pwd` | `PUT /user/{id}/reset-password` |
| 角色 | 分配用户 | `system:role:assign-user` | `PUT /role/{id}/users` |
| 角色 | 分配菜单 | `system:role:assign-menu` | `PUT /role/{id}/menus` |
| 角色 | 分配资源 | `system:role:assign-resource` | `PUT /role/{id}/resources` |
| 角色 | 分配用户组 | `system:role:assign-group` | `PUT /role/{id}/groups` |
| 角色 | 启用 / 停用 | `system:role:enable` / `system:role:disable` | `PUT /role/{id}/enable` `/disable` |
| 用户组 | 分配角色 | `system:group:assign-role` | `PUT /group/{id}/roles` |
| 用户组 | 分配用户 | `system:group:assign-user` | `PUT /group/{id}/users` |
| 用户组 | 维护上下级层级 | `system:group:assign-sub` | `PUT /group/{id}/sub-groups` `/parent-groups` |
| 用户组 | 删除 / 启停 | `system:group:delete` / `enable` / `disable` | 见 Controller |
| 菜单 | 关联资源（菜单授权） | `system:menu:assign-resource` | `PUT /menu/{id}/resources` |
| 菜单 | 启用 / 停用 | `system:menu:enable` / `system:menu:disable` | `PUT /menu/{id}/enable` `/disable` |
| 资源 | 关联菜单（资源授权） | `system:resource:assign-menu` | `PUT /resource/{id}/menus` |
| 资源 | 启用 / 停用 | `system:resource:enable` / `system:resource:disable` | `PUT /resource/{id}/enable` `/disable` |

### 2.2 「菜单授权」的两条路径（容易混淆，单独说明）

菜单授权在系统里有 **两个方向**，都已管控：

1. **角色 → 菜单**（谁看得到哪个页面）：`PUT /role/{id}/menus`，权限码 `system:role:assign-menu`
   —— 写 `basic_role_permission(type=1, ref_id=菜单id)`；
2. **菜单 → 资源**（这个页面能调哪些接口）：`PUT /menu/{id}/resources`，权限码 `system:menu:assign-resource`
   —— 写 `basic_menu_resource`；反向 `PUT /resource/{id}/menus` 同理。

## 3. 不需要权限管控的部分（需求 ②）

下列操作**只要登录就能做**，代码上刻意不加 `@PreAuthorize`：

| 操作 | 端点 |
|---|---|
| 用户新增 / 编辑 | `POST /user`、`PUT /user/{id}` |
| 角色新增 / 编辑 | `POST /role`、`PUT /role/{id}` |
| 用户组新增 / 编辑 | `POST /group`、`PUT /group/{id}` |
| 菜单新增 / 编辑 | `POST /menu`、`PUT /menu/{id}` |
| 资源新增 / 编辑 | `POST /resource`、`PUT /resource/{id}` |
| 应用 / 命名空间增删改 | `/app/**`、`/namespace/**` |
| **全部查询接口** | 所有 `GET` |

理由：这些是「录入型」动作，风险低、频次高，加权限码只会让日常运维处处卡壳；
真正有风险的是**把权限授予别人**（授权类）和**让账号失效**（删除/停用/改密），那些才管控。

## 5. 重置密码（需求 ④）

### 5.1 接口

```
PUT /api/system/basic/user/{id}/reset-password
Authorization: Bearer <token>
Content-Type: application/json

{ "password": "NewPass@123", "unlock": true }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `password` | 否 | 留空 → 回落到 `autumn.user.default-password`（默认 `Autumn@123456`） |
| `unlock` | 否 | 默认 `true`：顺带 `status=1` 并把 `login_error_count` 恢复满额 |

响应：`data.password` 为**实际生效的明文密码**，只在本次返回，供管理员转告用户。
校验：密码最短 8 位（`BasicUserService.MIN_PASSWORD_LENGTH`）。
权限：🔴 `system:user:reset-pwd`。

### 5.2 副作用

- `password` = BCrypt 新哈希
- `password_updated_at` = now（审计「上次改密时间」）
- `login_error_count` = 满额（`autumn.user.max-login-error-count`，默认 5；账号常常是输错被锁才来找管理员，改了密码还锁着会被当成重置失败）
- `status` = 1（仅 `unlock=true`）

### 5.3 安全处理

- **审计日志脱敏**：`OperLogInterceptor` 的跳过名单加入 `/reset-password`，
  否则明文密码会随 `request_data` 写进 `basic_oper_log`。
- **已知限制**：JWT 无状态，重置后旧 token 在 `jwt.expiration-ms`（默认 24h）内仍可用。
  若要求「改密即踢下线」，需要引入 token 版本号或黑名单——**本期不做**，记在 §9 待办。

## 6. 关键实现点（踩过的坑，务必保留）

### 6.1 超管必须带上完整 authorities

`@PreAuthorize("hasAuthority('x')")` 走的是 `Authentication#getAuthorities()` 的**字符串精确比对**，
看不懂我们自定义的 `"*"` 通配。原实现给超管的 authorities 只有 `["*"]`，
结果就是**「管理员反而一个按钮都用不了」**——这类 bug 极难排查。

修法（`PermissionService#doLoad` + `UserGrant#fullAccess(Collection)`）：
超管在短路返回时，把 `basic_menu` 里全部启用状态的 `menu_identification` 一起装配进来，
并额外保留 `"*"` 作为前端「全放行」的兼容信号。全量清单按 TTL 缓存（复用 `basic.rbac.cache-ttl-seconds`），
`evictAll()` 会一并清掉。

### 6.2 细粒度下沉到方法级，而不是 URL 资源表

`basic_resource` 用 `path + http_method + match_type` 匹配，
`PUT /user/{id}/reset-password` 与 `PUT /user/{id}` 在 prefix 粒度上**完全重叠**，
URL 层根本区分不开。所以：

- URL 资源层（可选严格模式）只负责「能不能调这一类接口」的粗收口；
- 「谁可以做这个动作」一律由 `@PreAuthorize` + 权限码决定。

对应开关：`basic.rbac.url-check`（默认 `false`）。

### 6.3 两个开关与回滚

| 配置 | 默认 | 作用 |
|---|---|---|
| `basic.rbac.enabled` | `true` | 总开关。`false` → 所有接口 permitAll（线上紧急回滚，改配置即可，不改代码） |
| `basic.rbac.url-check` | `false` | 是否叠加数据驱动的 URL 资源鉴权（`UrlAuthorizationManager`，默认拒绝） |

> 注意：`basic.rbac.enabled=false` 只放开**接口准入**，方法级 `@PreAuthorize` 对**已认证用户**仍然生效。
> 但因为超管恒直通，正常运维不会被锁死。若要彻底关掉方法级鉴权，注释掉
> `SecurityConfig` 上的 `@EnableMethodSecurity`（一处改动）。

### 6.4 前端按钮权限

- 后端 `/api/currentUser` 下发 `authorityList`（权限码清单）与 `superAdmin`；
- 前端 `store/modules/user` 把清单提到 store 顶层（原先指令读的是 `userStore.authorityList`，
  而数据躺在 `userStore.currentUser.authorityList`，**导致 v-auth 形同虚设**）；
- `v-auth` 指令：`清单含 "*"` 或 `含该权限码` → 显示；拿不到清单时**不隐藏**（可用优先，由后端 403 兜底）。

## 7. SQL 资产清单与执行顺序

全部位于 `autumn-gateway-dashboard/src/main/resources/`：

| 顺序 | 文件 | 作用 | 幂等 |
|---|---|---|---|
| 0 | `schema-basic-mysql.sql` | basic_* 12 张表 DDL | ✅ `CREATE TABLE IF NOT EXISTS`（`spring.sql.init` 启动时自动跑） |
| 1 | `db/rbac/V1__rbac_schema_mysql.sql` | 授权链路的**唯一键 + 索引**（存储过程探测，真正幂等） | ✅ |
| 2 | `db/rbac/V2__rbac_init_data_mysql.sql` | **菜单树 + 按钮权限点 + API 资源 + 菜单-资源关联 + 5 个角色 + 初始账号 + 授权矩阵** | ✅ `ON DUPLICATE KEY UPDATE` |
| 3 | `db/rbac/V3__rbac_reset_password_mysql.sql` | 收敛 `app_code`（`admin`→`dashboard`）+ 重置密码资源/关联/授权 + 更新菜单 1308 备注 | ✅ |
| — | `db/rbac/verify-mysql.sql` | 只读**一致性检查脚本** | — |
| — | `db/rbac/bootstrap-mysql.sh` | 一键自举脚本（按序跑 0→3，再跑检查） | ✅ |

> **菜单初始化数据就在 V2 的第 2 节**：目录 1101–1103、菜单 1201–1208、
> 按钮权限点 1301–1397（`system:user:create` 这类）。ID 段规划见 V2 文件头注释，
> 后续新增权限点请沿用 `<模块>段` 的留白区间，不要改动已有 ID。

### 7.1 一键自举（新库第一次使用）

```bash
# MySQL 跑在 Docker 容器里（本项目 192.168.0.102 的实际形态）
sh src/main/resources/db/rbac/bootstrap-mysql.sh --docker mysql -u root -p 123456 autumn-security

# 或者直接连实例
sh src/main/resources/db/rbac/bootstrap-mysql.sh -h 192.168.0.102 -u root -p 123456 autumn-security
```

脚本会先 `mysqldump` 备份（Docker 模式），再按序执行 0→3，最后跑 `verify-mysql.sql` 输出检查结果。

自举完成后的初始账号：

| 账号 | 密码 | 角色 |
|---|---|---|
| `admin` | `Autumn#Admin@2026` | 超级管理员（`admin=1` + `SUPER_ADMIN`），全权限直通 |
| `auditor` | `Autumn#User@2026` | 审计员，只读，用于验证「非管理员视角」 |

> ⚠️ 上线前必须改掉这两个密码。

### 7.2 手工执行（不想用脚本时）

```bash
mysql -uroot -p123456 autumn-security < src/main/resources/schema-basic-mysql.sql
mysql -uroot -p123456 autumn-security < src/main/resources/db/rbac/V1__rbac_schema_mysql.sql
mysql -uroot -p123456 autumn-security < src/main/resources/db/rbac/V2__rbac_init_data_mysql.sql
mysql -uroot -p123456 autumn-security < src/main/resources/db/rbac/V3__rbac_reset_password_mysql.sql
mysql -uroot -p123456 autumn-security < src/main/resources/db/rbac/verify-mysql.sql
```

（V1 用到了 `CREATE PROCEDURE`，需要具备相应权限的账号；应用账号 `admin` 无此权限时用 root。）

### 7.3 空库自举（不跑任何脚本）

`NamespaceDataInitializer`（`ApplicationRunner`，每次启动幂等执行）会：

1. 建默认租户 `default`；
2. 播种 `basic_app` / `basic_user(admin)` / `basic_role(admin, master=1)`；
3. **仅当 `basic_menu` 为空时**播种最小菜单集（避免与 V2 的完整菜单树重复，
   否则前端会出现两套同名路由、权限码也对不上）；
4. 播种两个演示用户组。

密码取 `autumn.user.default-password`（默认 `Autumn@123456`）。
这条路能登录，但**没有按钮权限点**，受控管理员角色拿不到任何权限——
正式使用请走 §7.1 / §7.2 的完整初始化。

## 8. 检查与排障

### 8.1 启动自检

启动时 `RbacStatusService#onReady` 会打印 RBAC 就绪状态；缺什么直接把原因列出来：

```
RBAC 未初始化完整，权限体系可能不可用：
  - basic_menu 无按钮权限点（menu_type=3）：@PreAuthorize 将全部拒绝
  - ...
自举方式：sh src/main/resources/db/rbac/bootstrap-mysql.sh --docker mysql
```

### 8.2 HTTP 检查接口（需登录）

```
GET /api/system/rbac/status   # 库里初始化到什么程度（menus/buttons/resources/roles/授权数/可登录账号/ready/problems）
GET /api/system/rbac/me       # 当前登录者的权限快照（userId/superAdmin/authorities）
```

### 8.3 常见症状对照

| 症状 | 原因 | 处理 |
|---|---|---|
| 登录后所有接口 401 | `SecurityContext` 仓库没生效 | 确认 `securityContext(...RequestAttributeSecurityContextRepository)` 在 `authorizeHttpRequests` **之前** |
| 超管也提示无权限 | 超管 authorities 只有 `"*"` | 见 §6.1，确认 `PermissionService` 已装配全量权限码 |
| 打开 `url-check=true` 后所有人 403 | `basic_resource.app_code` 与 `basic.rbac.app-code` 不一致 | 执行 `V3` 第 1 节收敛 `app_code` |
| 前端菜单出现两份「用户管理」 | `NamespaceDataInitializer` 与 V2 各造了一套菜单 | 已修：菜单非空时不再播种；存量重复数据需手工清理 |
| 授权改了但没生效 | 权限缓存未失效 | 写方法需挂 `@GrantChanged`；或等 `basic.rbac.cache-ttl-seconds`（默认 60s） |

### 8.4 回滚

1. 只想临时放开接口：`basic.rbac.enabled=false`，重启。
2. 想彻底关掉方法级鉴权：注释 `SecurityConfig` 上的 `@EnableMethodSecurity`。
3. 数据层面：改库前先 `mysqldump`（`bootstrap-mysql.sh` 在 Docker 模式下会自动备份到 `/tmp`）。
