**踩过的坑（别再踩）**：
1. **JJWT → Nimbus 编译报「程序包 org.springframework.security.oauth2.jwt 不存在」**：
   Spring Security 7 把 `oauth2.jwt` 放进了 `spring-security-oauth2-jose`，`spring-security-oauth2-resource-server` 不再传递它。依赖要直接引 **jose**。
2. **SAS 7（OAuth 2.1）强制 PKCE**：reactive 的授权请求解析器只对 `client_authentication_method=none` 自动加 PKCE，
   必须显式 `ClientSettings.builder().requireProofKey(true)`，否则 `invalid_request: OAuth 2.0 Parameter: code_challenge`。
3. **WebFlux 登出没有 `logoutRequestMatcher`**，方法名是 `requiresLogout(...)`。
4. **`ServerWebExchangeMatchers.pathMatchers(HttpMethod.GET, url)` 组合进 `OrServerWebExchangeMatcher` 后 GET 反而匹配不上**（POST 正常）。
   最终改为只按路径匹配 `pathMatchers(url)`。代价：GET 登出可被诱导（CSRF 式），网关已全局关 CSRF，接受。
5. **native 启动 0.12s 但请求 500**：`InvalidTypeIdException: ... java.util.Collections$UnmodifiableMap ... denied resolution`。
   表象像「JDK 内部类没注册」，**真因是 Spring Security 的 Jackson 模块 native 下反射实例化失败**
   （`SecurityJacksonModules.loadAndGetInstance` catch 掉异常只打 DEBUG）。
   排查命令：`./autumn-gateway-authorization --logging.level.org.springframework.security.jackson=DEBUG` → 满屏 `Cannot load module …`。
   修法：手写 RuntimeHints（保留作根因说明）+ **tracing agent 生成完整元数据**（真正兜底）。
   后续还会遇到 `Cannot construct instance of OAuth2TokenFormat`（mixin 也要反射），agent 方案一次解决。
6. `pkill -f 'autumn-gateway-authorization'` 会把**自己那条 ssh 命令**也杀掉（命令行含该字符串），必须加 `$` 锚定或按 PID 杀。

**核心结论**（后续实现按这个走，不要再重新论证）：
- 认证（签发令牌）**只在 `autumn-gateway-authorization`**；网关只做 JWKS 验签 + 身份透传 + 路由级粗粒度鉴权；细粒度/数据权限留给业务服务。
- 网关**不自己写登录**。客户端只跟网关打交道的诉求，用网关 `/auth/**` 代理端点透传给 authorization 来满足，签发点保持唯一，SSO 才成立。
- 网关鉴权**不用 `@PreAuthorize`**，用 `ReactiveAuthorizationManager` + `GatewayFilter`，起点参考 `autumn-gateway-examples-security-oidc` 的 `DynamicReactiveAuthorizationManager`。
- native 硬约束：网关侧 JWT 一律用 **Nimbus**，不引 JJWT。

**发现的 P0 隐患**：系统里存在两套互不认识的令牌 ——
dashboard 自签 HS256（`jwt.secret` 明文硬编码、sub=数字 userId、claims **无 authorities**）vs
authorization 签发 RS256（JWKS、sub=uuid、带 authorities）。

### 2. RBAC 权限数据诊断与补齐 —— 修复「admin 也没办法管理授权」（已完成 · 已执行到库 · 已验证）

**症状**：admin（`basic_user.admin=1`）登录后，角色管理的「分配菜单 / 分配资源」点不动，界面上看不到任何已授权项。

**根因**（这个结论很重要，别再排查一遍）：
`PermissionService#allMenuIdentifications` 从 `basic_menu.menu_identification` 取权限码装配超管的 authorities，
而库里 `menu_identification` 是**单段**的 `user` / `role` / `menu`，
代码 `PermCodes` 用的是**三段** `system:user:create`。
`@PreAuthorize` 走字符串精确比对 → 超管的 authorities 里根本没有 `system:role:assign-menu` → 全拒。
前端 `v-auth` 同理，授权按钮不渲染。

**补齐前的数据实况**：

| basic_menu（全部） | 13 | 54 |
| basic_menu（按钮 type=3） | **0** | 41 |
| basic_resource | 2 | 37 |
| basic_menu_resource | **0** | 48 |
| basic_role_permission | 3 | 197 |

### 3.1 待设计：令牌失效（用户提出，尚未实现）

需求：「一个用户一对密钥，无状态下让某个用户（如离职员工）立即停止访问」。

现状判断：per-user 密钥对**不推荐**（密钥数量随用户数膨胀、JWKS 变大、网关缓存刷新复杂）。
备选方案待与用户确认后再实现：
1. **短 TTL access_token（5–15 分钟）+ refresh_token 可撤销** —— 标准做法，成本最低
2. **token 版本号**：`user` 表加 `token_version`，JWT 带 `tv` claim，网关比对；离职时 `+1` 即全失效
3. **撤销集合**：网关本地缓存被撤销的 `(sub, min_iat)`，事件/轮询同步，秒级生效
4. SAS 自带 `/oauth2/revoke` 端点可吊销 refresh_token

建议组合：1 + 2（短 TTL 兜底 + 版本号做即时失效），网关侧缓存版本号即可，无需 per-user 密钥。
