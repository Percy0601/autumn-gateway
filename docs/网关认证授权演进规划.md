# Autumn Gateway 认证 / 授权 / SSO 演进规划

> 版本基线：Spring Boot 4.1.1 · Spring Cloud 2025.1.3（Gateway Server WebFlux 5.0.3）· Spring Security 7 · Java 25
> 终极目标：**全链路 GraalVM Native Image**（启动 < 1s、单二进制分发）
> 最后更新：2026-10-21

---

## 0. 一句话结论

| 关注点 | 归属 | 网关做什么 |
|---|---|---|
| 认证（你是谁 · 签发令牌） | **autumn-gateway-authorization** | 只校验，不签发 |
| 授权（你能干什么 · 粗粒度） | **autumn-gateway**（过滤器） | 路由级权限码判定 |
| 授权（细粒度 · 数据权限） | 业务服务 | 网关透传身份，不做判定 |
| SSO | **authorization**（集中会话） | 无状态，不参与 |

**不要在网关里再写一套登录。**

## 2. 认证放哪：分析与结论

### 2.1 你的理由里，成立的部分

> "app / 微信小程序未来是微信 OAuth2 客户端，微信登录后再在网关登录一下，轻量点。"

**「客户端只跟网关打交道」这个诉求完全成立**，但实现方式不是"网关自己签发"，而是：

- 网关暴露 `/auth/**` 代理端点，把凭据**透传给 authorization 的令牌端点**；
- 客户端拿到的是 authorization 签发的标准令牌，网关自身无状态；
- 效果上"看起来是在网关登录"，但签发点唯一 —— **SSO 才成立**。

### 2.2 为什么网关不能自己签发

1. **SSO 的前提是单一签发点。** 网关多实例部署，各自签发就是各自为政，跨应用免登直接失效。
2. **认证天然有状态。** 用户库、验证码、登录失败锁定、微信账号绑定（`user_auth_account`）—— 这些塞进网关，与"网关要轻、要 native、要小、要横向扩"直接冲突。
3. **微信回调带状态。** `state` 校验、session、绑定关系，WebFlux 无状态转发层做这套别扭且不必要。
4. **现在已经是两套了，不能变三套。** 见 §3。

### 2.3 结论

```
authorization  = 唯一 IdP：登录页 / 验证码 / 锁定 / 微信 / SSO 会话 / 签发 JWT
gateway        = OAuth2 Resource Server：JWKS 验签 + 身份透传 + 权限判定（无状态）
dashboard      = 权限与路由规则的权威数据源（不签发）
业务服务        = 消费透传身份，做细粒度与数据权限
```

## 3. ⚠️ P0 隐患：现在存在两套互不认识的令牌

这是**当前最危险的问题**，不解决，网关鉴权过滤器写完也是残的。

| | dashboard 自签 | authorization 签发 |
|---|---|---|
| 算法 | HS256 对称 | RS256 非对称 |
| 密钥 | `jwt.secret` 明文硬编码在 properties | JWKS 落 `oauth2_jwk` 表（可 file/memory） |
| `sub` | 数字 `userId` | 用户 `uuid` |
| claims | `userId` + `username`，**无 authorities** | `username`/`nickname`/`email`/**`authorities`** |
| 校验方式 | 共享密钥 | 公钥 JWKS |

后果：

- 网关要同时认 HS256 和 RS256，两套 `JwtDecoder`；
- `sub` 语义不一致（userId vs uuid），身份透传时无法统一；
- **dashboard 的 token 里没有 authorities**，网关想做鉴权就得回查库，而 authorization 的 token 已经自带 —— 两套逻辑。

**处理方案（建议 A）**：

- **A（推荐）**：dashboard 停止自签，改为 authorization 的 OAuth2 客户端（或 BFF 代理登录），统一走 RS256 + JWKS。dashboard 自身仍是 Resource Server，只校验。
- **B（过渡）**：网关做双 `JwtDecoder` 路由（按 `iss` 分派），同时给 dashboard token 补 authorities claim。短期可用，长期是技术债。

> 选 A 的话，dashboard 的登录/验证码/锁定能力可以直接下线，与 authorization 合并 ——
> 鉴权（`@PreAuthorize`）那套**保留不动**，它挂在 SecurityContext 上，与令牌来源解耦。

## 4. 授权分层：网关做到什么程度

```
┌─ 网关（粗粒度，数据驱动，本地缓存）───────────────┐
│  认证：token 有效？过期？iss 对不对？              │
│  授权：path + method → 需要哪个权限码？            │
│        用户 authorities 里有吗？超管直通？          │
│  不入：行级/列级数据权限、业务态判定                │
└────────────────────────────────────────────┘
                    ↓ 透传 X-User-Id / X-Authorities / 原 JWT
┌─ 业务服务（细粒度）────────────────────────────┐
│  数据权限、行级过滤、业务态（如"只能改自己的单"）   │
└────────────────────────────────────────────┘
```

要点：

- 复用 dashboard 已有的权限模型：`basic_menu.menu_identification`（权限码）、`basic_role_permission`、`basic_menu_resource`；
- 网关侧**不要**用 `@PreAuthorize`（网关没有业务方法），用 `ReactiveAuthorizationManager` + `GatewayFilter`；
- 参考现成实现：`autumn-gateway-examples-security-oidc` 的 `DynamicReactiveAuthorizationManager`；
- 权限数据：网关本地 Caffeine 缓存 + TTL/事件刷新，**不要每请求查库**；
- 开关必须保留：`autumn.authz.enabled`（总开关）、`fail-open/fail-closed`（故障时放行还是拒绝）—— 线上应急回滚能力；
- 超管直通 + 租户（`namespace_code`）隔离，对齐 dashboard 的 `UserGrant.fullAccess` 语义。

## 5. 微信场景澄清（实现前必须对齐）

三类微信登录**不是一回事**，现在 authorization 里做的是第 3 类：

| 场景 | 协议 | code 换什么 | 是否需要 OAuth2 客户端 |
|---|---|---|---|
| 微信小程序 | `jscode2session`（appid+secret） | `openid` + `session_key` | **否**，不是 OAuth2 |
| 公众号网页授权 | OAuth2 授权码（`snsapi_userinfo`） | access_token + 用户信息 | 是 |
| 开放平台扫码登录 | OAuth2 授权码（`snsapi_login`） | access_token + 用户信息 | 是（当前已实现） |

小程序路径：客户端拿 `code` → authorization 提供 `/login/wechat/miniapp` → 换 openid → 查/建 `user_auth_account` 绑定 → **签发自家 JWT**。
令牌格式与 Web 端完全一致，网关无需区分。

## 6. 分阶段路线图

### P0 — 身份体系收敛（阻塞后续一切）

- [ ] 关闭 `autumn.authorization-server.demo-client.enabled`（生产）
- 验收：全系统只有一把签发密钥、一个 `sub` 语义

### P1 — 网关认证（AuthN）
- [ ] `autumn-gateway-deploy` 引入 `spring-security-oauth2-resource-server`（reactive）

- 验收：无 token → 401；过期 → 401；合法 → 放行且下游能拿到身份

### P2 — 网关授权（AuthZ）
- [ ] 新建 `authz-autumn-gateway-starter`：`PermissionIndex`（path+method → 权限码）+ Caffeine 缓存

- [ ] 403 响应体统一（复用 dashboard 的 `Result` 结构）
- 验收：无权码 → 403；授权变更 TTL 内生效；关总开关立即全放行

### P3 — SSO
- [ ] authorization 集中会话（Spring Session JDBC，复用现有 MySQL）
- [ ] 多应用注册为 OAuth2 Client（`oauth2_registered_client`）
- [ ] 单点登出：RP-Initiated Logout + Back-Channel Logout

### P4 — 服务发现与配置

## 7. Native 化硬约束（每写一行新代码都要过）

| 约束 | 说明 |
|---|---|
| **不用 JJWT，用 Nimbus** | SAS 已在用 Nimbus；JJWT 的 impl/jackson 依赖反射，native 需额外 hints，没必要多一套 |
| 禁止运行时反射 / 动态代理 | JSON 用 `@JsonCreator` 或 JsonNode 遍历（config starter 已验证可行） |
| 禁止 AWT / ImageIO | 验证码已改为纯 SVG（`SecureRandom` 拼串），保持 |
| 资源文件显式注册 | Lua 脚本、静态资源走 `resources-config.json` / `include-resources` |
| HTTP 用 JDK `HttpClient` 或 WebClient | config starter 已用 JDK，保持 |
| 构建配方 | `mvn -Pnative,native-image -pl <module> package -DskipTests`，**禁用 `mvn native:compile`**（会跳过 process-aot，产物启动即 `ClassNotFoundException`） |
| 构建环境 | 102 虚拟机：GraalVM 25.0.3+9.1 + Maven 3.9.16 |

2. **权限码放 token 里还是网关查缓存？**
